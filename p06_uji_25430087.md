## 1. Ringkasan Eksekutif Pengujian Milestone Proyek 6

Dokumen ini disusun untuk memenuhi instrumen evaluasi **Tugas Mandiri: Milestone Proyek 6**. Pengujian dilakukan secara komprehensif pada basis data skala produksi `kopma_087` yang telah memuat 70 transaksi nota penjualan ($10 \times P$) yang tersebar pada 3 tanggal operasional berbeda (24, 25, 26 September 2026).

Metodologi pengujian mencakup:
1. **Verifikasi Uji Positif (*Positive Test Cases*):** Memastikan operasional kasir harian berjalan lancar, pencatatan transaksi anggota maupun pembeli umum diterima, serta integritas kaskade berjalan otomatis.
2. **Verifikasi Uji Negatif (*Negative Test Cases*):** Sedikitnya 5 skenario (diimplementasikan 8 skenario) yang memvalidasi bahwa kesalahan masukan, pelanggaran batas kuantitas personal $P+2=9$, duplikasi nomor nota, dan inkonsistensi referensial ditolak secara tegas oleh MariaDB/MySQL InnoDB dengan kode galat yang tepat.
3. **Dokumentasi Uji Gagal (*Failed Test Case* - Utang Desain Modul 14):** Satu skenario uji yang menunjukkan celah integritas aturan bisnis lintas-tabel (*cross-table business rule*) yang tidak dapat dijaga oleh DDL murni dan secara resmi dijadwalkan untuk diselesaikan via *Database Trigger* pada Modul 14.

## 4. Dokumentasi Skenario Uji yang GAGAL (Utang Desain Modul 14)

### 4.1 UJ-PROY-13: Penjualan Melebihi Ketersediaan Stok Fisik (AB-05)
- **Latar Belakang Kasus:**
  Aturan Bisnis **AB-05** menyatakan: *"Transaksi pembelian tidak dapat diproses jika stok barang kurang dari jumlah yang diminta."* Kasir Rina ingin membuktikan apakah sistem basis data secara mandiri menolak jika barang yang tersisa di rak fisik hanya 3 unit, namun dimasukkan transaksi penjualan sebanyak 8 unit.
- **Sintaks SQL Masukan:**
  ```sql
  USE kopma_087;

  -- 1. Kondisikan sisa stok barang nomor 15 (Cokelat Silverqueen) hanya tersisa 3 unit
  UPDATE barang SET stok_barang = 3 WHERE id_barang = 15;
  SELECT id_barang, nama_barang, stok_barang FROM barang WHERE id_barang = 15;

  -- 2. Kasir membuat nota baru
  INSERT INTO penjualan (no_nota_penjualan, tgl_penjualan, id_petugas, id_anggota, bayar_penjualan)
  VALUES ('PJ-TEST-OVERSTOK', '2026-09-27 11:30:00', 1, 1, 120000.00);
  SET @id_nota_baru = LAST_INSERT_ID();

  -- 3. Kasir memasukkan detail belanja sebanyak 8 unit (PADAHAL STOK HANYA 3)
  INSERT INTO detail_penjualan (id_penjualan, id_barang, qty_detail_penjualan, harga_satuan_detail_penjualan)
  VALUES (@id_nota_baru, 15, 8, 15000.00);

  -- 4. Periksa apakah baris diterima oleh basis data
  SELECT * FROM detail_penjualan WHERE id_penjualan = @id_nota_baru;
  ```

- **Salinan Layar Terminal (*Terminal Output*):**
  ```text
  +-----------+-------------------------+-------------+
  | id_barang | nama_barang             | stok_barang |
  +-----------+-------------------------+-------------+
  |        15 | Cokelat Silverqueen 62g |           3 |
  +-----------+-------------------------+-------------+
  1 row in set (0.001 sec)

  Query OK, 1 row affected (0.002 sec) -- Nota berhasil dibuat
  Query OK, 1 row affected (0.002 sec) -- DETAIL PENJUALAN BERHASIL MASUK!

  +--------------+-----------+----------------------+-------------------------------+
  | id_penjualan | id_barang | qty_detail_penjualan | harga_satuan_detail_penjualan |
  +--------------+-----------+----------------------+-------------------------------+
  |           75 |        15 |                    8 |                      15000.00 |
  +--------------+-----------+----------------------+-------------------------------+
  1 row in set (0.000 sec)
  ```

- **Evaluasi dan Status Pengujian:**
  - **Hasil yang Diharapkan Aturan Bisnis:** **DITOLAK (*Transaction Rejected*)** karena barang fisik yang tersedia di rak gudang tidak mencukupi permintaan transaksi.
  - **Hasil Nyata di Server DBMS:** **DITERIMA (*Query OK, 1 row affected*)**.
  - **Status Pengujian:** **GAGAL (*Test Failed*)** — Basis data pada tingkat DDL saat ini belum mampu menegakkan aturan ketersediaan stok fisik barang.

---

### 4.2 Analisis Kritis Keterbatasan DDL dan Pencatatan Utang Desain Modul 14
1. **Mengapa DDL `CHECK` Constraint Tidak Mampu Mencegahnya?**
   - Batasan `CONSTRAINT chk_barang_stok CHECK (stok_barang >= 0)` berada pada tabel `barang`, sedangkan operasi penambahan item belanja berlangsung pada tabel `detail_penjualan`.
   - Batasan pada tabel `detail_penjualan` (`CONSTRAINT ck_detail_qty CHECK (qty_detail_penjualan >= 1 AND qty_detail_penjualan <= 9)`) hanya memvalidasi apakah kuantitas yang dibeli berada dalam rentang 1 s.d 9 unit per item (*intra-row constraint*). Karena nilai 8 berada di antara 1 dan 9, batasan ini terpenuhi.
   - MariaDB dan MySQL InnoDB secara ketat **melarang penggunaan subquery pada klausul `CHECK`**. Oleh sebab itu, tabel `detail_penjualan` tidak dapat melakukan pembacaan (*cross-table query*) ke kolom `barang.stok_barang` pada saat `INSERT`.
2. **Pencatatan Resmi Utang Desain untuk Modul 14:**
   - Celah integritas ini secara formal ditetapkan sebagai **Utang Desain (*Design Debt*) Milestone Proyek 6** yang akan dituntaskan pada **Modul 14 (Triggers & Stored Procedures)**.
   - Pada Modul 14, aturan bisnis AB-05 akan dijaga secara absolut menggunakan *Trigger*:
     ```sql
     -- SOLUSI RESMI UNTUK MODUL 14 (DATABASE TRIGGER):
     DELIMITER $$
     CREATE TRIGGER trg_validasi_stok_sebelum_jual
     BEFORE INSERT ON detail_penjualan
     FOR EACH ROW
     BEGIN
         DECLARE v_stok_tersedia INT;
         
         SELECT stok_barang INTO v_stok_tersedia 
         FROM barang 
         WHERE id_barang = NEW.id_barang;
         
         IF NEW.qty_detail_penjualan > v_stok_tersedia THEN
             SIGNAL SQLSTATE '45000'
             SET MESSAGE_TEXT = 'Gagal Transaksi: Kuantitas beli melebihi ketersediaan stok fisik di rak!';
         END IF;
     END$$
     DELIMITER ;
     ```
